# Known issues · Відомі проблеми

What we found while testing, what was fixed and what is still open.
Що знайшли під час тестів, що виправлено і що ще відкрите.

## Open · Відкрито

| | Issue | Notes |
|---|---|---|
| 1 | **Unsigned installers.** Windows shows "Unknown publisher" when the MSI is started. | Only a paid code-signing certificate removes it. Check the file against `SHA256SUMS` from the release, or its Sigstore signature (README, "Check a download"). |
| 2 | **Setup wizard is English only.** | The panels are Ukrainian and English; the installer windows come from the MSI toolkit's stock dialogs. |
| 3 | **Builds are not byte-for-byte reproducible.** The MSI built by CI differs in size from one built on another machine. | Cause not investigated. Releases are built only by CI from the tag. |
| 4 | **WireGuard tests skip under `-race`.** gVisor's userspace network stack spins under the race detector (measured 745% CPU in `sleep.(*Sleeper).nextWaker`, 3% without). | Tunnel tests run without `-race` and in `internal/wgtun`; other end-to-end tests run over plain TLS under `-race`. |
| 5 | **Shop program runs on Windows only.** | macOS, Linux and Android shop programs are planned: same job protocol, a printing back-end per system. |
| 6 | **Document mode needs Windows at the shop** (XPS through the printer's own driver). | Receipt / label mode does not. |
| 7 | **The admin panel has no HTTPS.** | Matters only when it is open to the network; the emergency password from the network is off by default for this reason. Planned. |
| 9 | **"Paper size for everyone" (new in 0.19.0): the reset command for a user whose registry Windows has already unloaded was measured only in parts.** Measured on Windows 11 with the Xprinter XP-420B driver: the command resets users whose registry is loaded (one with a running program, one signed out 5 minutes before: Windows still kept it loaded), and both then print with the size for everyone; its load / delete / unload steps work on a saved copy of a user's registry and leave nothing loaded. Not measured: the whole command on a profile that was really unloaded. | The size itself is written by the service (measured on Windows Server 2019 and Windows 11). |
| 8 | **Flaky test `TestManageAndWatch`**: "session shutdown" on the first command to the shop (measured on 0.18.0: 1 of 15 runs of the end-to-end tests; 0 of 15 on 0.18.1, which does not show it is gone). | Test-only as far as known; cause not investigated. |

## Fixed · Виправлено

| Found | Problem | Fix |
|---|---|---|
| AI review, read in the code | **A shop computer with very many printers could not connect at all**: the list of its printers travels in one protocol line of at most 64 KB, a longer one was refused, and from a new address the refusals ended in a ban. Not reproduced on a real computer. | 0.19.0: the shop program cuts the list to fit, keeps the printers shared with the server in it and writes a warning to its log. |
| AI review, read in the code | **Removing a shop left things behind on the server**: its delivery worker kept waking up every few seconds, its events and counters stayed in memory. | 0.19.0: removed together with the shop. |
| AI review, read in the code | **The panel's web server had no limits on reading a request or on idle connections** (it matters when the panel is open to the network). **The log file was cut in the middle of a line** when it grew past its size limit, written in place. | 0.19.0: read and idle timeouts and a header size limit; the log is cut on a line boundary and swapped in through a temporary file. |
| CI, race detector | **`TestBanOverNetwork` failed once in CI** ("connection reset" for a valid code from a banned address); not reproduced in 600 local runs. Read in the code: a banned address has one handshake slot, and it was given back only after its connection was closed, so an immediate next connection could find it taken. | 0.19.0: the slot is given back before the connection is closed. Whether this was the cause of the CI failure is not proven. |
| AI review | **SECURITY.md did not say that the shop page takes a new connection code after any refusal by the server**, not only after the shop was removed. | 0.19.0: written down. |
| AI reviews (Sonnet, Mistral, Grok, GPT, Fable), read in the code | **Strangers could keep shops from reconnecting.** All 64 slots for unfinished handshakes were shared by everyone, a silent connection held one for 20 s, IPv6 addresses were counted one by one (a /64 has no end of them, so neither the per-address limit nor the ban worked), and connections through WireGuard took slots from the same total. Not tried as a live attack. | 0.18.1: failures, bans and slots count an IPv6 /64 as one address (old bans are moved over at the start); unknown addresses may hold 48 of the 64 slots, the rest is kept for allowed addresses and addresses of known shops; WireGuard has its own total; an unknown address gets 5 s for its greeting (known ones and WireGuard keep 20 s). |
| AI review (Sonnet), read in the code | **The server wrote its config to the disk on every connection of a shop**, synced, under the lock everything else waits for: after a server restart, one write per shop. The time this takes with hundreds of shops was not measured. | 0.18.1: written only when something changed (a new address, a lifted ban, a first connection); the "last seen" time of a known address once an hour. Queue files are synced as before. |
| AI review (Sonnet), read in the code | **A receipt could print twice** when the queue lifetime was set above 48 hours: the shop remembered printed jobs for 48 hours, the server could re-send one for up to 7 days (after a lost confirmation and a shop offline for over two days). | 0.18.1: every job tells the shop how long the server may still re-send it; the shop remembers printed jobs that long plus an hour, and never less than 48 hours. A shop program older than 0.18.1 keeps 48 hours. |
| AI reviews (Mistral, Fable), read in the code | **A damaged certificate file was silently replaced by a new certificate**, which turns away every shop at once (codes and keys are tied to it), with nothing in the log. | 0.18.1: a certificate is made only when both files are missing, and the log says so. Damaged or half-missing files stop the server with an explanation in server.log. The WireGuard key file is treated the same way: a file that is there but cannot be read is no longer replaced. |
| AI review (Fable), read in the code | **A job had 5 minutes to leave for the shop, whatever its size**, so a large document over a slow line could never arrive (not measured on a slow line). **The name typed into the sign-in form went to the log as it was**, line breaks included. **A shop's name and WireGuard key were read without the lock** while its connection was being set up. | 0.18.1: 2 minutes per 64 KB frame; the name is cut to 64 characters and kept on one line; both values are read under the lock. |
| AI reviews (Sonnet, Mistral, GPT) | **CI ran no race detector and no vulnerability check, vetted only the Windows build, and nothing updated the pinned actions.** | 0.18.1: `go test -race`, `govulncheck` for both builds and `go vet` for the host build on every push; Dependabot for actions and Go modules. |
| AI reviews (Mistral, Sonnet) | **SECURITY.md did not say what a stolen shop key gives**: the shop's receipts, since the last connection with a key wins. **The sign-out cookie had no HttpOnly / SameSite flags.** | 0.18.1: written down, with what narrows it; the cookie has the same flags as the sign-in one. |
| live test of 0.18.0 | **WireGuard on the server could stop for every shop until the service was restarted** (also in earlier versions). When a shop closed its tunnel and the server's next packet to it was answered "port unreachable", Windows reported an error on the server's UDP socket and the WireGuard library stopped receiving on it. Shops then stayed on plain TLS. Measured in the server's WireGuard log: `Failed to receive v4 packet: An existing connection was forcibly closed by the remote host`, `receive incoming v4 - stopped`. | 0.18.0: WireGuard uses Go's ordinary UDP sockets, which switch that Windows behaviour off. Measured after the fix: the shop reconnects over WireGuard with its new key. |
| AI reviews (Mistral, GPT) | **The connection code stayed valid until re-issued**: a code left in a chat or an installer log let anyone connect as that shop. | 0.18.0: the code works once. At the first connection the shop program gets its own long-term key; after it has connected with that key the code is refused. Reinstalling needs a new code from the panel. A shop program older than 0.18.0 keeps using its code. Tests: `TestOneTimeCode`, end-to-end exchange. |
| AI review (GPT) | **The service opened its ports while it was still SYSTEM**: the switch to the limited account ran in the background, 5 s after the start, on every start as SYSTEM (first install, every upgrade). | 0.18.0: the switch runs first; the process that is about to be restarted opens nothing. If the switch fails the service still prints as SYSTEM (by design), and its page now shows a warning, not only a log line. Test: `TestStartOrder`. |
| `-race` runs, AI review (Mistral) | **Flaky tests.** `TestResilienceStuckArrivalReleases` failed in cleanup (measured 9 of 30 runs under `-race`): closing the stuck connection turned it into a finished job that the server wrote to the spool while the test folder was being removed. `TestLocalClientCheck` was reported to fail on Linux with "connection reset by peer" at `Dial` (not reproduced on macOS). | Test-only. The stuck connection is reset and the test waits for the spool to empty (0 of 30 after). A reset during `Dial` while connections are refused is accepted as the expected outcome. |
| Go security release | **Built with Go 1.27.3**, one security release behind. | 0.18.0: Go 1.27.4; `govulncheck` reports no known vulnerabilities for the Windows and the test builds. |
| measured on a terminal server (0.17.0) | **Refusal of a program in a user session on the local printer ports was not measured live** (open item until now). | Measured: a plain PowerShell in an RDP session sent bytes to `127.0.0.1:9101`; the server refused it and logged "refused a connection to local port 127.0.0.1:9101: a program in user session #8 … Print only through a Windows printer". Nothing was printed. |
| AI reviews (Mistral, Grok, GPT) | **The emergency password was accepted from the network** over plain HTTP when the panel was open to the LAN. | 0.17.0: from other computers only when Settings allow it (off by default), with a clear-text warning. An upgraded server that relied on it must allow it once on the server itself. |
| AI reviews | **Sign-out and sign-in had no cross-site check**; **the shop key hash was compared with `==`**; **queue files were renamed without `fsync`** (a power cut at that moment could lose a receipt); **no Content-Security-Policy**. | 0.17.0: `X-SD` header required; constant-time compare; data synced before the rename; CSP on both pages. |
| AI review (GPT) | **CI could write to the repository on every push**, and actions were referenced by tag. | 0.17.0: a separate release job, tags only, has write access; actions are pinned to commit SHAs. |
| user's question about the firewall rule | **The program's firewall rule admitted any port and address** (by design: the service has no admin rights and cannot change rules), and **an upgrade recreated the rule**, so a rule narrowed by hand would have been opened again. | 0.16.0: an existing rule is kept on upgrade (only the program path is refreshed); Settings shows a PowerShell command that narrows both rules to the shops port and the shops' addresses, and whether the rule is narrowed. Measured: from another address the port is blocked after the command and stays blocked after an upgrade; undo opens it again. Giving the service Network Configuration Operators was measured to work but rejected: it would let a compromised service change the server's network settings. |
| user's test of 0.15.0 | **English panels showed Ukrainian lines** wherever a name in «» was part of the text (shop status line, "Add a printer to …", "New code for …", delete prompts): the quotes were switched to English ones before the translation was looked up, so no pattern matched. | 0.15.1: quotes switched after the lookup; a general pattern no longer hides a more specific one; the shop status line is translated sentence by sentence. Checked: every screen in English mode, no Cyrillic left. |
| user's install of 0.14.1 | **After installing, nothing showed that the program works**: no shortcuts, no icon next to the clock until the next sign-in, two exes with unclear names, no program icon. | 0.15.0: shortcuts in Start and on the desktop (shop: SlipDrukka, server: SlipDrukka panel); the finish window starts the icon next to the clock and offers to open the shop page / admin panel; files renamed to `SlipDrukka.exe` (icon and shop page) and `SlipDrukka-service.exe` (the service, no window); program icon on the exes, shortcuts and in Apps. A silent install (`/qn`) starts the icon at the next sign-in. |
| user's test | **The panels had no navigation history**: Back in the browser left the panel, F5 lost the section, the shop page was one long page. | 0.15.0: each section has its own address (`#settings`, `#journal`, `#shop-…`; shop page `#events`, `#log`), Back closes an open window first; the shop page got section tabs. |
| resilience tests | **Receipts could swap.** A job got its order number later, in the background, and a later job for the same printer could be delivered while an earlier one was still arriving from Windows (measured: the later one printed first). | Order number taken when the connection arrives; a job waits while an earlier job of its printer is arriving; an arriving job silent for 30 s, or broken off, no longer holds the others. Tests: `TestResilienceOrderWhileArriving`, `…BrokenArrivalDoesNotBlock`, `…StuckArrivalReleases`, `…ReconnectStorm`. |
| CI on Linux (UTC) | **CrowdSec log time was `…Z` in UTC**, while the shipped parser was verified with `+02:00`. | The log always writes a numeric offset (`+00:00`). |
| `-race` run | **Deadlock**: the log asked for its language under the lock that the code writing to the log already held. | Language read without that lock. |
| `-race` run | **A new code could close the point's own new WireGuard tunnel**: the old tunnel was closed in the background. | Old tunnel closed at once, before reconnecting. |
| measurement | **Adding a shop made the server forget where the other points were** for up to 25 s: peers were replaced as a whole. | Peers updated one by one. |
| live test | **Two tunnels with one key** during a reconnect made the server answer the wrong one. | One tunnel per point, kept between connections. |
| live test | **After one WireGuard failure the point stayed on TLS for 30 min.** | First retry after 1 min, then every 30 min. |
| first install of 0.14.0 | **Removal of 0.14.0 failed** (error 1603 / 2762): the cleanup step was placed before `InstallInitialize` by the MSI tool although it was asked for "before StopServices". | 0.14.1 pins the step to 1950 (after StopServices, before DeleteServices). Installing 0.14.1 over 0.14.0 fixes an existing install; then it can be removed normally. |
| uninstall on test machines | **Uninstall left the UDP firewall rule and an empty program folder.** | `cleanup` removes every rule; the installer runs it on removal. |
| first start | **A code set before the program started tore down the first session** right after it opened. | That reconnect request is dropped at start. |

## Tested by hand · Перевірено вручну

* Windows Server 2019 (server) and Windows 11 (shops): receipts over WireGuard
  and over TLS, falling back when UDP is blocked on the shop and coming back
  when it is open, bans after 5 failed connections, a banned address let in by
  a valid code, upgrade from older versions with points reconnecting by
  themselves.
* CrowdSec 1.8.2 (Linux container, a separate throwaway instance): the shipped
  parsers and scenario load, five lines give a ban, the server picks it up and
  drops it. CrowdSec on Windows not tested.
